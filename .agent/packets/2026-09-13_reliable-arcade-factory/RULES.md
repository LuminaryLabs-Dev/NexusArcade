# Shared execution and acceptance rules

1. **Authority:** specificIntent is authoritative. preparedInterpretation is a revisable proposal and may not remove requirements. Every change has an explicit revision and reason. Catalog/profile schemas reject unknown fields, unresolved references and executable model text.
2. **Technology:** Three.js rendering; implemented NexusEngine domains and explicitly local reusable adapters own gameplay. Thinking 1.2B plans/interprets; VL 3B writes structured decisions and reviews images. No model above 3B, arbitrary game scripts or manual generated-game edits.
3. **Deadline:** one persisted 1,500-second wall-clock deadline for each admitted idea. Queue wait after its request/admission, loading, compilation, inference, repairs and final per-game validation all count. Merely listing future uninstantiated batch slots does not start 100 simultaneous clocks. No cumulative token budget or fixed pass limit; bounded context, expansion depth and per-call timeout are operational safeguards. Retries/resume cannot reset the idea deadline. Atomic acceptance checks current time; expiry fails the idea, including after host suspension. Clock rollback cannot grant extra time.
4. **Shared work:** capability development is a goal prerequisite, outside per-game generation. Once a game is admitted, discovering a missing capability fails/blocks that idea; do not pause its timer for engine work. Future new attempts retain lineage and failure accounting.
5. **Recursive improvement:** component -> interaction -> loop -> whole game -> collection comparison. Prioritize findings; propose bounded changes; test affected dependencies; keep or revert; lock verified features. Locks bind to exact implementation/configuration/rule hashes. Changed features invalidate transitive dependents. Whole-game review still applies. Best verified is distinct from newest.
6. **Stop conditions:** acceptance, deadline, cancellation, unsupported capability, unresolved mandatory evidence, or repeated no-progress/oscillation. Preserve compact failed spine; never relabel failure to fill a quota. A later review can revoke acceptance. Repairing an artifact creates a traceable candidate, never a silent overwrite.
7. **Per-game baseline:** implemented connections; usable controls/camera; reachability/collision/visibility; consequential actions; concept contributions; objective/end/reset; adversarial actions; readable coherent presentation/feedback; visual AND interaction novelty; declared performance limits; exact-version evidence; regression and deadline compliance. All gates apply from the first batch. Later cycles add capability breadth, not delayed basic quality.
8. **Independent review:** validators own assertions; generator prose is not evidence. Required missing/contradictory judgments remain unresolved. Hold-out seeds, independent routes, negative cases and known near-duplicate controls challenge generator assumptions. Rubric/threshold versions freeze before runs; do not lower them to increase yield. Human/device judgments remain separate from model/browser checks.
9. **Counting:** ten disjoint batches each own 100 accepted slots. Pilots and historical games do not count. A game ID/version occupies at most one slot. Cross-batch duplicates and revoked entries leave unresolved slots. Replacement attempts have new IDs, shared parent lineage where applicable, and the full deadline/rubric; failed attempts remain reported. Collection acceptance is provisional until its paired review. Later collection audits are separate jobs and cannot retroactively extend a game's generation deadline.
10. **Queue:** planned -> ready -> running -> needs_review -> complete; blocked/failed/cancelled are explicit. Plan completion emits a bounded execution packet; Build completion emits candidates/evidence; Review completion requires all findings resolved or an explicit blocking verdict. Dependency invalidation prevents downstream admission. Rework attaches to the owning goal instead of resetting the entire queue. Atomic claim/checkpoint supports idempotent resume without duplicate builds.
11. **Storage:** keep accepted profile, compact spine and necessary evidence; share immutable runtime snapshots. Cap retained candidate artifacts to baseline/current plus required failure evidence; reference rather than duplicate captures. Retention does not erase acceptance provenance. No raw reasoning, weights or credentials.
12. **UI:** hero controls: generate, choose/play, return, understandable status. Advanced: seed, model/configuration details, queue evidence, failures and diagnostics. Do not expose raw implementation clutter in basic play. No changes to other repos, credentials, paid services or deployments are implied.
13. **Cleanup:** inspect references and produce a dry-run manifest; preserve accepted dependencies and required evidence. Broad/destructive deletion requires specific authorization when it is not already clearly covered. Goal 32 is planned cleanup, not permission to delete now.
14. **Acceptance parameters:** goal 01 must establish target hardware/resolution, loading/frame-time/memory budgets, supported inputs, visual/interaction novelty rubrics, human-review requirements and replacement/stall escalation rules. Calibrate with known good/bad cases. Unspecified mandatory parameters block batch readiness rather than becoming arbitrary defaults.
15. **Completion:** final reviewer verifies 1,000 active unique accepted slots, current evidence/rubric status, resolved mandatory findings and a usable arcade. Report acceptance rate across ALL attempts, per-game time distribution, failure categories, coverage, similarity clusters and regressions. No AAA or human-enjoyment claim without matching evidence.
