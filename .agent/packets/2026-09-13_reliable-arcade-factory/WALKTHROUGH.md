# Reliable Arcade Factory — complete execution walkthrough

## Summary

Use the four JSON contracts to finish a local harness that composes, styles, tests and presents 1,000 visually and behaviorally distinct Three.js/NexusEngine games. Execute 33 goals in eleven Plan -> Build -> Review cycles. The foundation contributes three pilot experiences; ten later Build goals each contribute 100 accepted slots.

This is an execution plan, not evidence that the future controller or expanded capabilities already work. Existing games retain their original evidence and do not count toward the new collection. Current source remains a narrower implementation. Start with G01; do not feed the entire queue to a model or launch 1,000 jobs at once.

Per admitted game idea: one 25-minute wall-clock deadline, no cumulative token allowance and no fixed improvement-pass limit. Expiry fails the idea. Shared capability development happens before admission. The campaign itself has no 25-minute limit. Repeated shared blockers stop admission instead of generating an endless stream of failures.

## Workflow: one goal at a time

1. **Restore context.** Read the current goal entry, its JSON references, last checkpoint and outstanding findings. Verify source/artifact/rule versions. Do not infer completion from a file or status label alone.
2. **Check readiness.** Confirm preceding review and required inputs remain valid. For G01, resolve input support, spatial tolerances, session coverage, concept/readability/presentation/novelty rubrics and device budgets. Record unknowns as blockers rather than defaults.
3. **Execute the Plan phase.** Produce the bounded execution packet: selected design, audited capabilities, exact module work, assertions, independent cases, coverage, rollback and handoff. A plan may document missing implementations but must specify how Build will provide them. It does not need evidence from future builds.
4. **Execute shared Build work.** Change only declared harness/kit/provider modules. Validate reusable capabilities before admitting game ideas. Add no freeform generated scripts. Use existing relevant checks and direct runtime/CLI verification; do not add unit/smoke test files unless separately authorized.
5. **Admit one idea.** Freeze seed, catalog, collection snapshot, capability versions and rubric. Persist original start/deadline before loading or inference. Uninstantiated future batch slots do not start clocks; any waiting after actual admission counts.
6. **Compile its profile.** Roll independent concepts; select compatible contextual layers; expand lazily; merge typed fragments; resolve exact domains, spatial graph, objective, presentation and assertions. Reject unsupported combinations before expensive work. Preserve the original concept intent throughout repair.
7. **Run bounded model tasks.** Thinking 1.2B receives a specific interpretation/repair issue and relevant contracts. VL 3B writes structured presentation choices and reviews actual images. Supply only relevant context, candidate revision and allowed paths. Enforce output shape, known IDs and protected requirements locally. No model above 3B or automatic acceptance from persuasive prose.
8. **Improve recursively.** Select the highest-priority finding; propose a compatible bounded patch; create a new candidate; recheck affected dependencies; keep only demonstrated improvement or revert. Lock exact verified features. Reopen the affected dependent group for integration failures. Advance component -> interaction -> loop -> whole game -> collection checks.
9. **Finish or fail the idea.** Schedule final validation while sufficient time remains. Check all required results, exact hashes, current collection novelty and original deadline atomically. No missing/uncertain required evidence becomes PASS. Failure preserves a compact spine and does not occupy an accepted slot.
10. **Complete Build handoff.** Emit candidate index, all attempts, evidence manifest, coverage, timings and findings. The target is provisional slots with per-game evidence, not merely 100 files. Give the paired Review goal exact artifacts and independent cases.
11. **Execute independent Review.** Use alternative routes, negative cases, matched views and nearest-neighbor comparisons. Inspect mandatory audio/human/device evidence separately. Review can revoke acceptance and send findings to the owning Plan or Build goal.
12. **Advance or rework.** Complete a cycle only with its mandatory findings resolved. Reconcile replacements and accepted slots; invalidate downstream readiness when necessary. Resume unaffected verified work. Stop batch admission on repeated shared blockers/no progress; do not blindly continue toward the number 1,000.

A later collection review does not extend the generation deadline. If it revokes a game, mark the slot unresolved. A materially revised or newly sampled replacement receives a new attempt ID and retains lineage; do not disguise continued repair of an expired unchanged idea as a fresh clock.

## Final outcome

- A usable arcade with clear Generate, choose/play, Back, restart and status flows; advanced configuration and diagnostics remain secondary.
- A resumable local queue with accurate goal, attempt and slot accounting; interruption does not duplicate work or reset deadlines.
- A versioned capability catalog and compiler supporting layered randomization without requiring models to solve integration from scratch.
- A structured profile and compact evidence spine for every game, including concept contributions, exact dependencies and permitted repairs.
- A recursive controller that protects verified behavior, reopens affected features, reverts regressions and stops failed ideas honestly.
- Exactly 1,000 active, distinct, accepted collection slots across ten batches; pilots, historical games, duplicates and revoked attempts are excluded.
- Distinct appearance AND consequential player interactions supported by comparative evidence. A thousand names, seeds or recolors is insufficient.
- Safe artifact retention: accepted dependencies and essential evidence preserved; disposable outputs removed only under an explicit authorized manifest.
- Reports distinguish schema/source checks, automated play, image review, audio, target-device performance and human judgments. AAA fidelity or enjoyment is not claimed without appropriate evidence.

These are acceptance targets, not a guarantee that the currently available domains can achieve them. Failure to meet them blocks completion rather than relaxing the definition.

## Full working and validation checklist

### Before execution
- [ ] All four JSON files parse; IDs, references, dependency order and version hashes resolve.
- [ ] Queue has 33 goals and exactly ten 100-game batch targets.
- [ ] Runtime consumers implement the JSON contracts; editing JSON alone has not enabled them.
- [ ] G01 resolves eight mandatory calibration records with concrete values/cases and rationale.
- [ ] Three feasible pilot briefs differ in world organization, decisions and visual composition.
- [ ] Required capability gaps have named owners and implementation/probe work before admission.
- [ ] Per-phase evidence is appropriate: Plan specifies; Build produces; Review challenges.

### Before each goal and idea
- [ ] Prerequisite goals, evidence and source versions remain current.
- [ ] Authoritative intent and editable interpretation are separate; scope/exclusions are clear.
- [ ] Outputs, checks, failure owner and handoff are specified.
- [ ] All mandatory planning decisions resolve before Build readiness.
- [ ] Catalog options are eligible by evidence, not merely marked source-present.
- [ ] Types, units, bounds, cardinality, child references and compatibility pass.
- [ ] Profile records selected options and all derived/default decisions with provenance.
- [ ] No fragment overwrite, hidden concept removal or unsupported capability is allowed.
- [ ] Concrete request starts one persisted deadline; loading, waiting and repairs count.
- [ ] Profile exposes exact controls, viewpoint, world, domains, connections and endings.

### During generation and improvement
- [ ] Model identity/size and local endpoint meet policy.
- [ ] Calls receive only relevant contracts, findings, evidence and permitted edit paths.
- [ ] Unknown fields, stale revisions, arbitrary code and protected edits are rejected.
- [ ] Each patch states the targeted finding and expected check improvement.
- [ ] Failed attempts and rejected patches retain compact reasons and lineage.
- [ ] Changed features invalidate affected dependent locks and stale evidence.
- [ ] Unaffected evidence is reused only when its version/hash dependencies still match.
- [ ] Keep/revert uses observed outcomes; positive wording or equal scores are insufficient.
- [ ] Repeated patches, oscillation and exhausted supported alternatives stop ineffective work.
- [ ] Final validation time is preserved; checks are never skipped to meet the clock.

### Required per-game checks
- [ ] Composition: every capability, parameter and typed connection is implemented and valid.
- [ ] Controls: movement, targeting, camera, input release and focus recovery work.
- [ ] Spatial: objectives are reachable; collision, clearance, gates and visibility hold.
- [ ] Loop: declared success/failure paths and full restart behave correctly.
- [ ] Resilience: repeated, interrupted, invalid and alternative-order actions preserve rules.
- [ ] Concept: each mandatory concept contributes an observed consequence.
- [ ] Readability: intent, interactive targets, progress and consequences meet frozen criteria.
- [ ] Presentation: coherent geometry, materials, lighting, motion and audio support play.
- [ ] Novelty: both visual identity and player decisions differ from nearest accepted neighbors.
- [ ] Performance: concrete target-device loading, frame-time and memory budgets pass.
- [ ] Regression: protected behavior remains valid after changes and integrated review.
- [ ] Evidence: artifact/rule/input versions match; uncertain or missing results cannot pass.
- [ ] Deadline: final atomic acceptance occurs before original start plus 1,500 seconds.

### Review, recovery and delivery
- [ ] Independent cases can reject candidates despite generator confidence.
- [ ] Known duplicates/recolors and graph relabelings fail calibrated novelty controls.
- [ ] Image evidence is not substituted for audio, gameplay or human understanding.
- [ ] Expiry, cancellation, crashes, suspension and clock anomalies cannot grant acceptance.
- [ ] Resume verifies lease ownership and checkpoint state without duplicating attempts.
- [ ] Revocations remove accepted counts and invalidate dependent readiness.
- [ ] Replacement IDs/lineage are explicit; one artifact occupies at most one slot.
- [ ] Shared fixes trigger appropriate regression/migration decisions for pinned older games.
- [ ] All-attempt acceptance rate, timing distribution and failure causes are reported.
- [ ] Cleanup dry run resolves artifact references and preserves accepted dependencies.
- [ ] Final arcade startup, browsing, launch, Back, restart and diagnostics work on target.
- [ ] All 1,000 slots and required evidence reconcile; no unresolved mandatory finding remains.
